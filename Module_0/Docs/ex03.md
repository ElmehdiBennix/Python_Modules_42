# Exercice 03 — Nothing to see here

## The problem

`NULL_not_found` classifies Python's null-like values. `None` prints `Nothing`,
`NaN` prints `Cheese`, integer `0` prints `Zero`, the empty string prints
`Empty`, and `False` prints `Fake`; every one of those returns `0`. Anything
else prints `Type not Found`, with a capital `F`, and returns `1`. Each label
line also shows the type, except the empty string, which prints only
`Empty: <class 'str'>` so the line keeps a single space. The tester output is:

```text
Nothing: None <class 'NoneType'>
Cheese: nan <class 'float'>
Zero: 0 <class 'int'>
Empty: <class 'str'>
Fake: False <class 'bool'>
Type not Found
1
```

## The concept

The label depends on the value and on the exact type, and the types overlap in
ways that punish a naive order. `False == 0` is true, `0.0 == 0` is true, and
`bool` subclasses `int`. A chain that compares values first labels `False` as
`Zero`, so the exact type checks have to come first and narrow the comparison.

`None` is a singleton, so the honest question is `object is None`, not
equality. For `NaN`, equality is useless in the other direction: `NaN != NaN`
is true by definition, so the test is self-inequality, `object != object`,
guarded by `type(object) is float`. That avoids importing `math` just to call
`isnan`, and it keeps the exercise to plain comparisons.

The empty-string branch prints only the type because the value is invisible;
including it would leave a double space after the colon. The fallback text is
`Type not Found`, which differs from ex02's `Type not found` only in
capitalisation, and the subject compares characters.

## How to check

Run the tester and expect all six lines. Run the float zero call and expect the
fallback, which proves `0.0` is not treated as `Zero`. Run the `True` call and
expect `Type not Found`, which proves booleans are not integers here.

```bash
cd Module_0/ex03
python3 tester.py                                     # six lines above
python3 -c "from NULL_not_found import NULL_not_found; \
print(NULL_not_found(0.0))"                           # Type not Found, then 1
cd .. && .venv/bin/flake8 ex03/NULL_not_found.py
```

Expect nothing from the lint command: a clean file prints nothing.


These one-liners show why the checks must be narrow:

```bash
python3 -c "print(False == 0, 0.0 == 0, type(False) is int)"
True True False
python3 -c "x=float('nan'); print(x == x, x != x)"
False True
```

Value equality groups values that the exercise separates. Exact type checks
before equality keep `False` out of the integer-zero branch and keep `0.0`
out of it as well. NaN needs its self-inequality property, but a type guard is
still required so an unusual object with a custom comparison cannot be
misclassified. `None` uses identity because it is a singleton sentinel.

The empty string is a visual edge case. Printing the value after the colon
would produce an extra blank, so the required line contains only its type.
The fallback return value makes invalid input observable to a caller even
when its output is only one short line. Test each neighboring case, not only
the five named values, because the boundaries are the lesson.

## Key take away

Equality is broader than identity, and Python's numeric tower makes that
difference visible. Ordering conditions from most specific type to least
specific prevents a later branch from stealing an earlier case. Some values
cannot be detected by comparison and need a structural property instead.
Falling back deliberately, with a distinct message and a distinct return code,
turns an unhandled input into a defined outcome. Reading the subject's spelling
is part of the specification.
