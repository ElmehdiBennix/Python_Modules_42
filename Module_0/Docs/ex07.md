# Exercice 07 — Filtering words

## The problem

The program receives a string and an integer. It prints the list of words in
the string whose length is strictly greater than the integer, so
`'Hello the World'` with `4` gives `['Hello', 'World']` and with `99` gives
`[]`. A wrong argument count or a second argument that is not an integer prints
`AssertionError: the arguments are bad`. The subject also requires at least one
list comprehension and one lambda, which is the real point of the exercise.

## The concept

A comprehension has the shape `[expression for item in iterable if condition]`.
The condition is evaluated for each item and the expression decides what lands
in the result. `str.split()` with no argument splits on runs of whitespace, so
repeated spaces and leading spaces collapse without extra handling.

A lambda is an expression that produces a function value. A bare lambda in a
condition is a function object, and function objects are always truthy, so the
condition must call it: `(lambda x: len(x) > n)(w)`. The same value can be
handed to `filter` instead, which calls it once per item.

The integer conversion belongs outside the comprehension. `int(sys.argv[2])`
can raise `ValueError`, and doing it once means a bad argument fails before any
output rather than half way through the loop. It also avoids converting the
same text once per word.

Style rules interact with the requirement. Assigning the lambda to a name
triggers flake8 `E731`, which forbids that form, so the lambda stays inline or
becomes an argument.

## How to check

Run the two filtering calls and expect a two-word list, then an empty list. Run
the bad calls and expect the assertion line rather than a traceback.

```bash
cd Module_0/ex07
python3 filterstring.py 'Hello the World' 4    # ['Hello', 'World']
python3 filterstring.py 'Hello the World' 99   # []
python3 filterstring.py 3 'Hello the World'    # AssertionError: the arguments are bad
python3 filterstring.py                        # AssertionError: the arguments are bad
cd .. && .venv/bin/flake8 ex07/filterstring.py
```

Expect nothing from the lint command: a clean file prints nothing.


The required expression can be reduced to a one-line experiment:

```bash
python3 -c "n=3; print([w for w in 'a four seven'.split() if (lambda x: len(x)>n)(w)])"
['four', 'seven']
```

The lambda expression creates a function, and the following parentheses call
it for the current word. Omitting that call would leave a function object in
the condition; function objects are truthy, so every word would pass. The
comparison is strict, which excludes a word whose length equals the threshold.

`split()` with no separator treats any run of whitespace as a boundary and
does not create empty words for leading or repeated spaces. Conversion of the
threshold happens once before the comprehension. That both avoids repeated
work and ensures invalid input fails before a result is printed. The exact
argument count is checked first, so a missing or extra value reaches the same
required assertion line rather than a traceback.

## Key take away

A lambda is a value, not a call, and forgetting the parentheses silently
changes a test into a constant. Convert and validate arguments once, before the
work begins, so failure cannot happen part way through. `split()` already
handles irregular whitespace, which removes a manual parsing step. An empty
result is still a result and must be printed. Lint rules sometimes conflict
with an exercise requirement, and the resolution is to keep the required form
where it is allowed.
