# Exercice 09 — Your first package

## The problem

The goal is a real installable package named `ft_package`, version `0.0.1`,
with one public function `count_in_list`. The layout puts the implementation in
`src/ft_package/count_in_list.py` and re-exports it from `__init__.py` with
`__all__`. The project carries `pyproject.toml`, `README.md` and `LICENSE`.
After installation, `from ft_package import count_in_list` must work and
`pip show -v ft_package` must describe the package, including its summary,
author email and version.

## The concept

A package is a directory containing `__init__.py`. That file runs on import and
is the right place to expose a public name, so callers never reach into the
module that defines it. The `pyproject.toml` has two jobs: `[project]` holds
metadata such as name, version, description and author, and `[build-system]`
names the backend, here `setuptools.build_meta`.

`uv build` writes two artifacts into `dist/`: a wheel and a source distribution.
The wheel is essentially an installable archive, while the sdist contains the
source plus build metadata and must be built before it can be installed.
Installing the sdist makes pip construct it in an isolated environment and
fetch the backend, so it exercises `pyproject.toml`; installing the wheel does
not.

A uv environment has no `pip` unless it is created with `uv venv --seed`, which
matters when the check uses `pip show`. That command reads installed metadata
from the `.dist-info` directory, not from the working tree, so editing the
configuration without rebuilding shows stale values. Modern setuptools also
folds identity into `Author-email: eagle <eagle@42.fr>`, leaves `Author:` empty
and writes metadata version 2.4, which differs from the 2022 sample in the
subject without being an error.

## How to check

Run the build from `ex09` and expect both filenames in `dist/`. Run the install
into a separate environment and expect the count `2`.

```bash
cd Module_0/ex09
uv build --out-dir dist        # ft_package-0.0.1-py3-none-any.whl and .tar.gz
ls dist
cd /tmp && uv venv --seed /tmp/pkgtest
uv pip install --python /tmp/pkgtest/bin/python \
  /home/$USER/Projects/Python_Modules_42/Module_0/ex09/dist/ft_package-0.0.1-py3-none-any.whl
/tmp/pkgtest/bin/python -c "from ft_package import count_in_list; \
print(count_in_list(['toto', 'tata', 'toto'], 'toto'))"   # 2
/tmp/pkgtest/bin/pip show -v ft_package
cd /home/$USER/Projects/Python_Modules_42/Module_0 && .venv/bin/flake8 ex09/src
```

Expect nothing from the lint command: a clean tree prints nothing.


PEP 621 metadata and installed metadata answer related but different
questions. The source declaration can be inspected with:

```bash
python3 -c "import tomllib; print(tomllib.load(open('pyproject.toml','rb'))['project']['version'])"
0.0.1
```

That reads the project file only. After a wheel is installed, `pip show -v
ft_package` reads the generated `.dist-info` record. If the version or
description was changed without rebuilding and reinstalling, `pip show`
continues to report the old installed value. This is why a package check must
name its artifact and use a separate environment or a clean reinstall.

The wheel is ready for installation; the sdist is a source archive that lets
the build backend run again. Both should be built because they test different
paths. A `src` layout also makes the import location explicit, but only when
the test runs outside the source directory. The public import is the
re-export in `__init__.py`, while the counting implementation remains in its
own module. `__all__` documents that intended surface without changing the
counting behavior.

## Key take away

Packaging turns code into an artifact with identity, and the metadata is data
that can be inspected independently of the files. The sdist and the wheel test
different things, so both are worth installing. Test from outside the source
directory, otherwise the local tree shadows the installed copy. Reading
`pip show` is reading the installed record, not the repository, and stale
records are the usual explanation for surprising output. Modern tooling may
normalise metadata differently from an older sample, so compare values rather
than formatting.
