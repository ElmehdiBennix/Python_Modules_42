# Exercice 00 — First script

## The problem

Four containers each hold `"Hello"` plus a throwaway second value, and each one
must become a greeting by changing the existing object rather than retyping the
final literal. The list receives `"World!"`, the tuple must end as
`("Hello", "France!")`, the set must contain `"Hello"` and `"Angouleme"`, and
the dict must map `"Hello"` to `"42Angouleme!"`. The four prints at the bottom
of the file stay untouched, so the output is fixed:

```text
['Hello', 'World!']
('Hello', 'France!')
{'Hello', 'Angouleme'}
{'Hello': '42Angouleme!'}
```

The set line carries no guaranteed order, so `{'Angouleme', 'Hello'}` is
equally correct.

## The concept

Mutability belongs to the container, not to the value it holds. A list is
mutable, so `ft_list.append("World!")` extends the existing object and every
reference to that list sees the change. A set is mutable too, so it accepts
`remove` and `add`, but it deduplicates on construction and keeps no index.

A tuple and a string are immutable. There is no `ft_tuple[1] = "France!"`; the
only way to "change" a slot is to build a new object from a slice plus a
one-element tuple:

```python
ft_tuple = ft_tuple[:1] + ("France!",)
```

The comma is load-bearing. `("France!")` is a string in parentheses, and adding
it to a tuple raises `TypeError`; `("France!",)` is a tuple. Dictionaries join
the mutable group, and `ft_dict["Hello"] = "42Angouleme!"` replaces the value
behind an existing key.

The printed order of a set comes from hashing, and Python randomises string
hashes per process unless `PYTHONHASHSEED` is set. Two runs on the same machine
can print the two names in different orders, and both are correct.

## How to check

Run the script from its own directory, then run it again and compare. Expect
only the set line to move; the other three lines are stable.

```bash
cd Module_0/ex00
python3 Hello.py                    # four lines, set order may vary
python3 Hello.py                    # the set line may swap
PYTHONHASHSEED=0 python3 Hello.py   # fixed seed, reproducible order
cd .. && .venv/bin/flake8 ex00/Hello.py
```

Run the lint command from `Module_0`. Expect nothing from it: a clean file
prints nothing.


One short experiment separates mutation from rebinding:

```bash
python3 -c "a=[1]; b=a; a.append(2); print(a, b, a is b)"
[1, 2] [1, 2] True
python3 -c "a=(1,); b=a; a += (2,); print(a, b, a is b)"
(1, 2) (1,) False
```

The first assignment gives two names for one list, so `append` is visible
through both names. The tuple has no mutating `append` operation; `+=` creates
a new tuple and binds it to `a`, leaving `b` attached to the original object.
The exercise's slice expression uses the same replacement idea. A set and a
dictionary remain mutable, but their APIs differ: a set adds or removes
members, while a dictionary updates a value by key. A set cannot be indexed,
and a dictionary preserves insertion order for iteration without promising
that a set printout has a fixed order.

The requested values therefore test four separate choices, not four spellings
of one operation. Keep the existing names and perform the smallest operation
that reaches each target. That makes the printed result easy to compare and
keeps the mutation lesson visible in the source.

## Key take away

The container decides which operations exist, so choosing a type is choosing an
editing model. Slicing plus concatenation is the general recipe for producing a
modified immutable value, and a one-element tuple needs its trailing comma.
Set order is an implementation detail, and fixing the seed is only worth it for
a stable screenshot. The distinction between mutating an object and rebinding a
name explains every line of this exercise.
