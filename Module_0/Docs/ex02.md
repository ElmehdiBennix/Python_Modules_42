# Exercice 02 — Types in the kitchen

## The problem

One function, `all_thing_is_obj`, prints a label describing the type of whatever
it receives and returns `42`. Lists, tuples, sets and dicts print `List`,
`Tuple`, `Set` and `Dict` followed by the type, strings print the odd
`Brian is in the kitchen : <class 'str'>` line, and every other value prints
`Type not found`. The tester covers the whole set:

```text
List : <class 'list'>
Tuple : <class 'tuple'>
Set : <class 'set'>
Dict : <class 'dict'>
Brian is in the kitchen : <class 'str'>
Type not found
42
```

The return value is `42` on every path, including the fallback. Importing the
module must print nothing.

## The concept

The natural shape is a dispatch table rather than a chain of `if` statements.
Class objects are hashable and are instances of `type`, so they work as dict
keys:

```python
labels = {list: "List", tuple: "Tuple", set: "Set", dict: "Dict"}
label = labels.get(type(object))
```

`type(object)` returns the class of the instance, for example `<class 'list'>`.
Using `.get()` returns `None` for a missing key instead of raising `KeyError`,
which is what makes the fallback branch possible.

The important distinction is `type(x) is C` against `isinstance(x, C)`. The
first asks for the exact class; the second accepts subclasses. A class that
inherits from `list` is caught by `isinstance` but not by `type(x) is list`, and
the subject wants the narrow answer. The same asymmetry explains why `bool`
slips into integer checks: `bool` subclasses `int`, so `isinstance(True, int)`
is true while `type(True) is int` is false.

Strings need their own branch because the message embeds the value. It is still
an exact type check, not an `isinstance` call, and the fallback covers ints,
floats, booleans and `None` alike.

## How to check

Run the tester and expect the seven lines above. Run the extra call and expect
`Type not found` followed by `42`, which proves the fallback returns the right
value.

```bash
cd Module_0/ex02
python3 tester.py                                     # seven lines above
python3 -c "from find_ft_type import all_thing_is_obj; \
print(all_thing_is_obj(10))"                          # Type not found, then 42
cd .. && .venv/bin/flake8 ex02/find_ft_type.py
```

Expect nothing from the lint command: a clean file prints nothing.


Class objects can be inspected directly:

```bash
python3 -c "print(type([]), type('x') is str, type(True) is int)"
<class 'list'> True False
```

The last result matters because `bool` inherits from `int`, but exact type
dispatch intentionally rejects it as an integer. Equality would not provide
that distinction: `True == 1` is true. The same issue appears whenever a
subclass carries behavior that should not receive the label for its parent.

The dictionary of labels is data-driven, yet the string branch still needs its
special message because the value belongs in the output. Calling the function
through an import is a useful check: the module's top level defines names but
does not print. Calling it with an unsupported value checks both the fallback
line and the invariant return value. The return is independent of the label,
so callers can rely on `42` even when the displayed classification is
unknown.

## Key take away

Exact type checks answer a different question than subclass checks, and the
subject's wording decides which one is correct. A dictionary keyed by class
objects turns a branching classifier into data, which is easier to extend and
to read. Defaults matter: `.get()` with a sentinel keeps the unknown case
explicit. Side effects belong behind the call, so importing a module should
never produce output.
