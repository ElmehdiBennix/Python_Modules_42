# Exercice 01 — The timestamp

## The problem

The script takes no input and prints two lines. The first reports the current
Unix timestamp twice, once with thousands separators and four decimals, then in
scientific notation with two decimals, both taken from the same instant:
`Seconds since January 1, 1970: 1,666,355,857.3622 or 1.67e+09 in scientific
notation`. The second line prints today's date in the `Oct 21 2022` shape.
There is no argument handling and no error path; the only real failure mode is
a timestamp sampled twice.

## The concept

`time.time()` returns a float: seconds since 1 January 1970 UTC, independent of
the local timezone. The format spec does the presentation work. `{value:,.4f}`
means fixed point with four digits after the dot and a comma every three
digits, while `{value:.2e}` means scientific notation with two digits after the
dot.

The value must be read once into a variable before either placeholder is
filled. Two calls return two different instants, and after rounding the halves
of the line can disagree. That looks like a formatting bug but is a sampling
bug, and it is invisible most of the time.

The date comes from `time.strftime("%b %d %Y")`, where `%b` is the abbreviated
month name supplied by the current locale. The default C locale gives `Oct`; a
machine configured for another language gives that language's abbreviation,
which is worth knowing before comparing output with a neighbour.

The label "Seconds since January 1, 1970" is literal text inside the f-string.
Nothing computes it from the timestamp, and the epoch is simply the definition
the library follows.

## How to check

Run the script and expect the date line to match `date`. Run it twice and
expect the numbers to advance by roughly a second. Expect no trailing space at
the end of the first line, which `cat -e` makes visible.

```bash
cd Module_0/ex01
python3 format_ft_time.py             # timestamp line, then today's date
python3 format_ft_time.py | cat -e    # $ marks the line end
date                                  # same day as the second line
cd .. && .venv/bin/flake8 ex01/format_ft_time.py
```

Expect nothing from the lint command: a clean file prints nothing.


The formatting can be isolated from the clock:

```bash
python3 -c "x=1234567.89123; print(f'{x:,.4f}'); print(f'{x:.2e}')"
1,234,567.8912
1.23e+06
```

The comma flag groups the integer part and the `f` conversion fixes the
number of fractional digits. The `e` conversion changes the notation, not
the underlying value. Reading `time.time()` once is therefore a data
consistency rule: both renderings describe the same sample even if formatting
takes measurable time.

`strftime` works with local time for the date line, while the Unix timestamp
is defined as elapsed seconds from the UTC epoch. The displayed calendar date
can therefore depend on the machine's timezone near midnight. `%b` also
comes from the active locale. A check should compare the shape and the
current date rather than copy a stale number from a previous run.

## Key take away

A value sampled at two different moments is two values, so read it once and
reuse it. Format specs separate data from presentation, which is why one float
can appear as money and as scientific notation in the same sentence. Locale
settings leak into date formatting through names such as `%b`, so output that
depends on the month is not portable by default. Text that looks computed may
be a literal, and reading the subject closely is cheaper than reverse
engineering the string.
