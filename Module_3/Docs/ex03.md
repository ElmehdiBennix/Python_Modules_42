# Exercice 03 — Calculator, vector and scalar

## The problem

Write a `calculator` class that holds a list of floats and applies a scalar to
every element. Four operations are required: addition, multiplication,
subtraction and true division, each implemented through the matching dunder,
each printing the resulting list and returning `None`. The tester applies one
operation per object, then subtracts and divides the same object in sequence.
Division by zero is the only handled error; other input is trusted.

## The concept

Operators are syntax for method calls, and the interpreter resolves the method
on the type. `v + 3` becomes `type(v).__add__(v, 3)`; the left operand supplies
both the type and the first argument. If that call returns `NotImplemented`,
Python tries the reflected operation on the right operand, `type(3).__radd__(3, v)`.
Here the asymmetry is visible: `v + 3` works, while `3 + v` fails with
`TypeError: unsupported operand type(s) for +: 'int' and 'calculator'`, because
`int.__add__(3, v)` returns `NotImplemented` and `calculator` defines no
`__radd__`. The operator protocol is not symmetric unless both sides implement
it.

The declared return type is `None`, and the methods honour it by falling off the
end after `print`. Returning `None` from a dunder is legal; the expression simply
evaluates to `None`. `print('result:', v + 3)` prints `[4.0]` from inside the
method and then `result: None`. That value is not inert. `v + 3 + 3` raises
`TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'`, because the
second `+` receives `None`. Augmented assignment follows the same path: `v += 5`
looks for `__iadd__`, finds none (`hasattr(calculator, '__iadd__')` is `False`),
falls back to `__add__`, and rebinds `v` to the returned `None`. The list is
updated, but the name no longer refers to a calculator.

The methods mutate `self.numbers` in place, writing each computed value back at
its index. That is observable through aliasing: after `nums = [1.0, 2.0]`,
`v = calculator(nums)` and `v * 5`, `nums` prints `[5.0, 10.0]` and
`v.numbers is nums` is `True`. The constructor stores the caller's list rather
than a copy, so the caller sees every operation. The tester depends on the
mutation: after `v3 - 5` prints `[5.0, 10.0, 15.0]`, `v3 / 5` must print
`[1.0, 2.0, 3.0]`, which only happens if the subtraction was stored. Returning a
fresh list without storing it would leave `self.numbers` unchanged, and the next
operation would divide the original values.

Division checks the scalar before the loop. That placement matters for an empty
vector: no element division would occur, so a guard inside the loop would never
fire, while the current guard raises anyway; `calculator([]) / 0` still produces
the error. This repository raises `decimal.DivisionByZero`, not the built-in
`ZeroDivisionError`. The two are related: the MRO is
`decimal.DivisionByZero, decimal.DecimalException, ZeroDivisionError,
ArithmeticError, Exception, BaseException, object`, so `except ZeroDivisionError`
catches it. The traceback nevertheless names `decimal.DivisionByZero`, which
belongs to decimal arithmetic, not to division of floats. The subject asks for
division-by-zero handling without naming a type; a plain `ZeroDivisionError`
would be the idiomatic signal here.

The subject's tester contains `Print("---")` with a capital P, which would raise
`NameError`; the tester in this repository uses lowercase `print`, so the
separators actually appear. Other bad input, such as adding a string, raises
whatever the underlying arithmetic raises; the subject explicitly leaves that
unhandled.

## Key take away

A dunder is the hook the interpreter uses for syntax, and its signature is the
protocol. Returning `None` from an arithmetic dunder is legal but makes the
expression useless downstream, so a chain or an augmented assignment can
silently replace the object with `None`. Mutation versus replacement is
observable through the tester: read the sequence of operations, not only the
first line. Guard the case that can fail before the loop that would hide it, and
know which exception class is actually raised. Follow the repository's tester
over a typo in the subject text.
