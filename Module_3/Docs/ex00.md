# Exercice 00 — GOT S1E9

## The problem

Build an abstract `Character` class whose constructor takes `first_name` and an
optional `is_alive` defaulting to `True`, plus a `die` method that moves the
character from alive to dead. A `Stark` subclass inherits from it and supplies
the behaviour. The base must stay unusable: `Character("hodor")` has to raise
`TypeError` naming the missing abstract method, while `Stark("Ned")` and
`Stark("Lyanna", False)` both work.

## The concept

`@abstractmethod` does not create a new kind of function. It sets
`__isabstractmethod__ = True` on the function object and returns the function
unchanged; `Character.die.__isabstractmethod__` prints `True`. The flag matters
later, at class creation, when `ABCMeta` runs as the metaclass. `ABCMeta.__new__`
scans the namespace, collects every name whose value carries that flag, and also
pulls in abstract names inherited from bases that the subclass has not
overridden. It stores the result in the class attribute `__abstractmethods__`.
For `Character` the set is `frozenset({'die'})`; for `Stark`, which defines
`die`, it is `frozenset()`.

The enforcement lives in `object.__new__`, not in `ABCMeta` and not in the
`@abstractmethod` decorator. When an instance is requested, `object.__new__`
checks the class's `__abstractmethods__`; while the set is non-empty it raises
before `__init__` runs. That is why the message names construction:
`TypeError: Can't instantiate abstract class Character without an implementation
for abstract method 'die'`. Calling `object.__new__(Character)` directly
produces the same error, which shows the gate is the allocator. `Character.die`
keeps a body, so `super().die()` is callable from a subclass, but that body only
raises `NotImplementedError`; no `Character` object exists to call it on.

The check is deferred, not applied to subclassing. A subclass that adds no `die`
is created without complaint and keeps the inherited abstract name:
`Sub = type('Sub', (Character,), {})` yields
`Sub.__abstractmethods__ == frozenset({'die'})`, and the failure appears only at
`Sub('x')`. That timing is deliberate: a class can be defined in one module and
completed by a mixin elsewhere, and the interpreter waits until someone asks for
an object. An incomplete subclass can therefore be imported and inspected; only
construction fails.

`Stark("Ned").__dict__` prints `{'first_name': 'Ned', 'is_alive': True}`, and
`'die' in Stark("Ned").__dict__` is `False`. That mapping is the instance
namespace written by `__init__`. `die` lives in `Stark.__dict__` and in
`Character.__dict__` as a function. Reading `Ned.die` walks the MRO, finds that
function on the class, and returns a bound method that inserts `Ned` as `self`;
the function itself is not copied into the instance. Docstrings follow the same
path: `Ned.__doc__` is the class docstring, `Ned.__init__.__doc__` the
constructor's, `Ned.die.__doc__` the method's.

`is_alive: bool = True` is evaluated once when the `def __init__` statement
runs and stored in the function's defaults: `Stark.__init__.__defaults__` prints
`(True,)`. Every call that omits the argument reads that same object. `die`
writes `False` into `self.is_alive`, so it creates an instance attribute when
one is absent and rebinds the existing one otherwise; it never touches the
default. A class attribute would be shared by every instance, which is why the
default belongs on the constructor.

## How to check

The tester must run inside the exercise directory so `S1E9` resolves locally.

```bash
cd Module_3/ex00
../.venv/bin/python tester.py
# {'first_name': 'Ned', 'is_alive': True}
# True
# False
# Representing the Stark family.
# (constructor docstring, multi-line)
# (die docstring, multi-line)
# ---
# {'first_name': 'Lyanna', 'is_alive': False}

../.venv/bin/python -c 'from S1E9 import Character; Character("hodor")'
# TypeError: Can't instantiate abstract class Character without an
# implementation for abstract method 'die'

cd .. && .venv/bin/flake8 ex00
# a clean tree prints nothing
```

Python 3.10 keeps the source indentation in those docstrings; the system
interpreter here (3.14) strips the common indent before exposing `__doc__`, so
the same print looks flatter under that interpreter.

## Key take away

An abstract method is a promise the base class makes to its callers: every
subclass will answer that name. The interpreter enforces the promise at
instantiation, which turns a design mistake into a `TypeError` at construction
instead of an `AttributeError` deep inside a method. Instance data and class
behaviour live in different mappings, and `__dict__` shows exactly which is
which. Docstrings are data too, reachable through attribute lookup. Keep the
shared default on the base constructor so it exists in one place.
