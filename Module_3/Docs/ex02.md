# Exercice 02 — DiamondTrap

## The problem

Build `King(Baratheon, Lannister)`, a class that inherits two families at once,
and give it a way to change the king's eyes and hair after construction and read
the values back. The tester prints the method resolution order, the instance
`__dict__` on creation, the two getters after the setters run, and the
`__dict__` again to show what changed.

## The concept

Two parents that share a grandparent form a diamond: `King` reaches `Character`
through both `Baratheon` and `Lannister`. Python resolves the ambiguity with C3
linearisation. It merges the parents' MROs and the direct bases, taking the head
of the first list only when that name appears in no other list's tail. Here it
starts with
`[King] + merge([Baratheon, Character, ABC, object],
[Lannister, Character, ABC, object], [Baratheon, Lannister])`.
`Baratheon` is a valid head, so it comes first. `Character` is now the head of
the first list but sits in the tail of the second, so it is skipped; `Lannister`
is a valid head and comes next. `Character`, `ABC` and `object` follow. The
stored tuple is
`(King, Baratheon, Lannister, Character, ABC, object)`, which
`print(King.__mro__)` shows.

`super()` is not "the parent". It is a cursor that starts after the class where
the method is defined, in the MRO of the instance's actual type. In a `King`,
`Baratheon.__init__`'s `super()` therefore lands on `Lannister.__init__`, not on
`Character.__init__`:
`super(Baratheon, King("J")).__init__.__qualname__` prints `Lannister.__init__`.
`Lannister.__init__` calls `super()` again and reaches `Character.__init__`,
which runs once. Counting calls to `Character.__init__` during `King("J")` gives
`1`; two independent parent constructors would run it twice.

The order of assignments explains the default traits. Execution descends the
MRO to `Character`, which writes `first_name` and `is_alive`; on the way back,
`Lannister` writes blue eyes and light hair, then `Baratheon` writes brown eyes
and dark hair. The last writer is `Baratheon`, the first base in the class
statement, so `King("J").__dict__` shows `'family_name': 'baratheon'`,
`'eyes': 'brown'`, `'hairs': 'dark'`. Reversing the bases would reverse the
winner, not just the printed MRO.

A `property` stores a getter and an optional setter and defines `__set__` even
when the setter is absent; assignment then raises `AttributeError`. Because
`object.__getattribute__` checks data descriptors before the instance
`__dict__`, a property cannot be shadowed by an instance entry. Writing
`x.__dict__['p'] = 'raw'` then reading `x.p` still runs the getter; the `'p'`
entry stays unused. `@x.setter` builds a second property object with a setter function
attached, and assignment then runs that function. A setter that stores `_v`
leaves `{'_v': 5}` in the instance dictionary, not `{'p': 5}`.

This repository does not use properties. `get_eyes`, `set_eyes`, `get_hairs`
and `set_hairs` are ordinary methods; `type(King.__dict__['get_eyes'])` prints
`<class 'function'>`, not `<class 'property'>`. The tester's calls work, but
plain assignment bypasses the check:
`king.eyes = 'green'` writes `'green'` into `king.__dict__`, and the
`isinstance` guard in `set_eyes` never runs. The subject asks for
properties, so this is a real deviation in mechanism, not only in style.

The tester also differs from the subject. It prints `King.__mro__`, which the
subject's tester does not, and it wraps the whole body in `except TypeError`.
That wrapper catches genuine errors from the constructor: `King(1)` raises
`TypeError: first name must be a str type`, and inside the tester the message
becomes `King Error: first name must be a str type` while the run continues.
The subject's sample also shows `'hair'` in the first dictionary and `'hairs'`
in the second; the code uses `hairs` in both.

## Key take away

The MRO is data, not folklore: print it when a diamond behaves unexpectedly.
C3 keeps each class ahead of its ancestors and turns the base list into a single
order, so a shared ancestor runs once. `super()` follows the instance's MRO, so
a constructor in the middle of a diamond calls the next class, not its own
parent, and the first base is the last writer. A property and a getter/setter
pair can produce identical output through explicit calls, but only the property
makes plain assignment go through validation. Read the tester for additions that
can hide failures, especially a broad `except`.
