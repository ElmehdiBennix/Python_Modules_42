# Exercice 02 — My first decorating

## The problem

`callLimit(limit)` returns a decorator. Applied to a function, it produces a
function that runs at most `limit` times. Every later call must print
`Error: <function ...> call too many times` and must not run the body. The allowed
functions are `None`, so `functools` is out and `functools.wraps` cannot be used.

The tester decorates `f` with a limit of three and `g` with a limit of one, then
calls both three times in a loop. Each decorated function needs its own counter,
even when two limits happen to have the same value.

## The concept

`@callLimit(3)` is not one call, it is two:

```python
def f():
    print("f()")


f = callLimit(3)(f)
```

`callLimit(3)` runs first and must return a callable; that callable receives `f`
and must return another callable; the name `f` is then rebound to the second
result. After decoration the name `f` means the innermost function, and the
original body is reachable only through the closure parameter `function`.

Three moments, three scopes:

| Scope | Runs | Owns |
| --- | --- | --- |
| `callLimit(limit)` | once, at `@callLimit(3)` | `limit` and `count` |
| `callLimiter(function)` | once, when `def f` finishes | the original function |
| `limit_function()` | on every call of `f` | nothing |

The counter belongs one level above the wrapper. Because `count` is created in
`callLimit`, reusing a single `callLimiter` object on two functions shares one
allowance, while two separate `@callLimit(...)` expressions create two cells. The
subject's prototype puts `count = 0` in `callLimit`, so the shared behaviour is
the specified one, not an accident.

Inside the wrapper, the order of the three statements is the correctness proof.
The guard runs first, so a rejected call cannot consume an allowance; `count += 1`
runs only on the permitted path, so the counter equals the number of calls the
decorator allowed. The increment sits before the call, so an attempt that raises
still consumes its allowance, which is the behaviour of a quota. Incrementing before
the guard would need `> limit` instead of `>= limit` to pass the tester, and would
leave the counter drifting upward on every rejected call.

The wrapper must also be transparent: `return function(*args, **kwds)` forwards
the arguments and the return value. Writing `function(*args, **kwds)` without the
`return` turns every decorated function into one that returns `None`, which the
tester cannot detect because `f` and `g` return nothing.

`nonlocal count` is mandatory. `count` is local to `callLimit`, and an assignment
in `limit_function` would otherwise create a new local for the whole body, making
the read raise `UnboundLocalError`.

## How to check

Run the tester from its directory. The address in the error varies per run.

```bash
cd Module_4/ex02
../.venv/bin/python tester.py
# f()
# g()
# f()
# Error: <function g at 0x...> call too many times
# f()
# Error: <function g at 0x...> call too many times
```

`f()` appears three times, `g()` once, and no body runs after its limit.

A decorated function that takes arguments and returns a value proves the wrapper
is transparent. The third call is rejected:

```bash
../.venv/bin/python -c \
  "from callLimit import callLimit
@callLimit(2)
def add(a, b):
    return a + b
print(add(1, 2)); print(add(3, 4)); print(add(5, 6))"
# 3
# 7
# Error: <function add at 0x...> call too many times
# None
```

The counter can be read from the closure after five calls to a function limited to
one. The cells are `count`, `function` and `limit`, so the first value stays at one
even though four calls were rejected. Each rejection prints its own line, so the
four errors come before the list:

```bash
../.venv/bin/python -c \
  "from callLimit import callLimit
@callLimit(1)
def d():
    return 'ran'
for _ in range(5):
    d()
print([cell.cell_contents for cell in d.__closure__])"
# Error: <function d at 0x...> call too many times
# Error: <function d at 0x...> call too many times
# Error: <function d at 0x...> call too many times
# Error: <function d at 0x...> call too many times
# [1, <function d at 0x...>, 1]
```

The subject requires a docstring on every function, including the two nested ones:

```bash
../.venv/bin/python -c "from callLimit import callLimit; print(callLimit.__doc__)"
```

Lint from the module root:

```bash
cd Module_4
.venv/bin/flake8 ex00 ex01 ex02 ex03
```

Expect nothing: a clean tree prints nothing. flake8 does not check the subject's
docstring rule either, and `functools.wraps` is unavailable, so the decorated
function keeps the wrapper's `__name__`; that is a known cost of
`Allowed functions : None`.

## Key take away

A decorator factory is not three nested functions for their own sake: each level
exists because a value arrives at a different time. Configuration arrives at the
`@` expression, the function arrives when the `def` is executed, and arguments
arrive at each call. State that must survive between calls lives in a closure cell
and needs `nonlocal` to be mutated. The guard protects the allowance, the increment
records the permitted attempt, and the `return` keeps the decorated function
indistinguishable from the original.
