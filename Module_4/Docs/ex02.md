# Exercice 02 — My first decorating

## The problem

The exercise asks for a decorator factory named `callLimit`. It receives an
integer limit and returns a decorator. Applying that decorator to a function
must allow the function to run only up to the requested number of calls. Later
calls must be blocked and must print an error instead of executing the wrapped
function.

The tester creates two independently limited functions:

```python
@callLimit(3)
def f():
    print("f()")


@callLimit(1)
def g():
    print("g()")
```

It calls both functions three times. The expected subject behavior is that
`f()` prints three times, while `g()` prints once and then reports that the
function was called too many times. Each decorated function needs its own
counter, even when two limits happen to have the same value.

## The concept

A decorator is a callable transformation. The syntax `@decorator` above a
function is equivalent to assigning the result of the decorator back to the
function name:

```python
def f():
    pass

f = decorator(f)
```

The decorator factory adds one more call level. `callLimit(3)` runs first and
returns `callLimiter`; then `callLimiter(f)` runs when Python processes the
decorated definition and returns `limit_function`. Calls made later reach that
wrapper. This separation lets the limit be fixed during decoration while the
number of completed calls changes during execution.

The counter belongs in a closure. A function creates a local namespace for
each call, but a nested function can retain an enclosing variable after the
outer function returns. The retained variable is stored in a closure cell.
The wrapper reads the counter, compares it with the limit, prints the error
when the limit has been reached, and increments the counter only when it
actually permits the wrapped function to run. Incrementing after the call
keeps the count equal to successful executions.

The factory must run once for each `@callLimit(...)` expression. If one
decorator object is reused for two functions, its captured counter is shared
and the two functions consume the same allowance. Separate factory calls
create separate cells, so `f` can have three permitted calls while `g` has
one. This is the reason the state belongs inside the factory rather than in a
module-level variable.

The wrapper uses `*args` and `**kwds` so the decorator can preserve arbitrary
function signatures. It must not call the wrapped function after the limit,
because printing the function body would make the rejection ineffective.
The subject allows no helper library: the behavior comes from nested
functions, closure state, comparison, and a conditional return.

## Key take away

Decorators replace function names with returned callables. A decorator factory
creates configuration once, while its wrapper changes captured state on each
call. Closures provide private per-decoration counters, and forwarding
`*args` and `**kwds` keeps the wrapper general. Validate both the permitted
calls and the blocked calls, because a decorator is correct only when it
controls execution rather than merely printing a message.
