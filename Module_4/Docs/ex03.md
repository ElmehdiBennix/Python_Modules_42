# Exercice 03 — Data class

## The problem

`Student` is a dataclass built from a `name` and a `surname`. It sets `active` to
`True`, derives a `login` from the name and surname, and generates a fifteen-letter
lower-case `id` with the supplied `generate_id` function. The derived fields must
not be accepted by the constructor, and the subject forbids writing `__str__` or
`__repr__`.

The expected representation shows the fields in declaration order:

```text
Student(name='Edward', surname='agle', active=True, login='Eagle', id='...')
```

Constructing with `id="toto"` must raise
`TypeError: Student.__init__() got an unexpected keyword argument 'id'`.

## The concept

`@dataclass` is a class decorator that reads annotated attributes and generates
`__init__`, `__repr__` and `__eq__` from them. The annotations are the schema: an
attribute assigned in a hand-written `__init__` but never annotated at class level
is invisible to the decorator, which then generates a constructor with no
parameters and a representation with no fields.

The generated constructor only accepts fields whose `init` is true. Marking a field
`field(init=False)` is therefore the same statement as "this value is derived":
`login` and `id` stay out of the signature while remaining real attributes that
`print` shows.

Derived values need the input fields to exist first, which is what
`__post_init__` is for. The generated `__init__` calls it as its last step, after
`name` and `surname` are bound, so the login can be computed there.

Declaration order matters twice. It is the `__repr__` order, which must match the
expected output, and it is constrained by the rule that a field without a default
cannot follow one with a default. `name` and `surname` come first, then the
defaulted `active`, then the two derived fields.

`default` and `default_factory` differ in when the value is created. `default` is
an expression evaluated once while the class body runs, so every instance would
share one object; `default_factory` stores a callable and calls it per instance.
`field(default_factory=generate_id)` is therefore correct, while
`field(default=generate_id())` freezes a single identifier at import time and gives
every student the same one. Dataclasses refuse a mutable default such as `[]`, but
they cannot detect this timing mistake because a string is immutable.

The login rule has to be read off the expected output rather than guessed from the
field name. `name="Edward"` and `surname="agle"` produce `Eagle`: the first letter
of the name, upper-cased, followed by the whole surname.

The subject forbids `__str__` and `__repr__` because the exercise is about shaping
the generated representation through field declarations. A hand-written `__repr__`
hardcodes the expected string, so it would pass the test even if the fields were
wrong, in the wrong order, or missing. It would also drift as soon as a field is
added. `__str__` is forbidden for the same reason: `str()` already falls back to
`__repr__`.

## How to check

Run the tester from its directory. The identifier changes on every run.

```bash
cd Module_4/ex03
../.venv/bin/python tester.py
# Student(name='Edward', surname='agle', active=True, login='Eagle', id='...')
# Student(name='mehdi', surname='bennix', active=True, login='Mbennix', id='...')
```

Both lines print `active=True`, because the class-level default is copied into each
instance when the constructor runs. Assigning `student.active = False` afterwards
would change that object only: the default is never mutated, only rebound.

The forbidden constructor argument is checked separately, because it ends the
script:

```bash
../.venv/bin/python -c \
  "from new_student import Student; Student(name='Edward', surname='agle', id='toto')"
# TypeError: Student.__init__() got an unexpected keyword argument 'id'
```

Two instances in one run must receive different identifiers, which is what proves
`default_factory` is doing its job:

```bash
../.venv/bin/python -c \
  "from new_student import Student
first = Student(name='A', surname='b')
second = Student(name='C', surname='d')
print(first.id, second.id, first.id != second.id)"
# <fifteen letters> <fifteen letters> True
```

Lint from the module root:

```bash
cd Module_4
.venv/bin/flake8 ex00 ex01 ex02 ex03
```

Expect nothing: a clean tree prints nothing. flake8 cannot check the documentation
rule either, so the subject's requirement is verified by hand:

```bash
cd Module_4/ex03
../.venv/bin/python -c "from new_student import Student; print(Student.__doc__)"
```

## Key take away

A dataclass turns annotated state into a constructor and a representation, so the
field declarations are the design and the generated methods are the consequence.
`field(init=False)` separates caller input from derived state, and `__post_init__`
is where derived values are computed once the inputs exist. Use `default_factory`
for anything that must differ per instance, and leave `__repr__` generated: a
hand-written one satisfies the test while hiding the mistake it was meant to catch.
