# Exercice 01 — Outer_inner

## The problem

Three functions. `square(x)` returns `x ** 2`, `pow(x)` returns `x ** x`, and
`outer(x, function)` takes a number and a function and returns an object that, on
each call, applies `function` to the latest value and returns the result, so the
next call continues from there. Scalar numbers only: anything else raises
`TypeError`, and booleans count as anything else because `bool` subclasses `int`.
Globals are forbidden.

## The concept

`outer` is a closure factory. Each call creates a frame holding `x`, `count` and
`function`, then defines `inner` in that frame and returns it. `inner` is what the
caller receives; `outer`'s frame is gone, but the names `inner` uses are stored in
cells, so `inner.__closure__` keeps them alive. `inner.__code__.co_freevars`
names those cells. Two calls to `outer` create two sets of cells, which is why two
counters from the same factory stay independent.

The important line is `x = function(x)`. `inner` reads the enclosing `x` and
rebinds it, so the value returned by one call becomes the argument of the next.
The square chain is `3 -> 9 -> 81 -> 6561`; the power chain starts at `1.5` and
compounds from its own previous result. That is the compounding the exercise asks
for: the closure remembers the latest value, not the original argument.

Assignment decides scope at compile time. Without `nonlocal x`, the assignment
`x = ...` makes `x` local to `inner` for the whole body, so the read on the right
hand side happens before the local exists and raises `UnboundLocalError`. The
subject's "no global" rule removes the other tempting fix: `global x` would let
the chain work, but it would move the state into the module namespace, where every
function shares it and it outlives the closure. `nonlocal x` keeps the state in
the cell that belongs to this `inner`. The chain then works because that cell is
shared by every call of the same `inner`.

`square` and `pow` are ordinary functions, so they are values like any other.
`outer` does not know which one it receives; it calls whatever is in its
`function` cell. Passing `square` to one `outer` call and `pow` to another is what
lets one wrapper serve two behaviours, and a lambda works for the same reason.

The current code also carries `count`, incremented on every call and never
consulted. Its cell reaches `3` after the square chain, but no branch, return or
print depends on it, and a copy of `inner` without `count` produces the same
`9, 81, 6561`. It is dead state: harmless, but it suggests a limit that the
function never enforces. The type guard is the other boundary. `bool` is a
subclass of `int`, so `isinstance(True, int)` is true; the check must reject
booleans explicitly, and `square('a')` must raise `TypeError("Error")` rather
than return a value or a different exception.

## Key take away

State that outlives one call belongs in an enclosing scope, and mutating it needs
an explicit `nonlocal`. A closure is a counter with no module-level name to
collide with, and each factory call gets a fresh cell. Rebinding a captured name
is what makes the chain compound, so returning the new value is part of the
contract. Type guards belong at the boundary, and `bool` needs naming because it
is an `int`. Two closures from one factory prove the state is not shared.
