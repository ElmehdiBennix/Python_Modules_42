# Exercice 01 — Outer_inner

## The problem

Three functions. `square(x)` returns `x ** 2`, `pow(x)` returns `x ** x`, and
`outer(x, function)` returns a callable that applies `function` to the latest value
on every call, so each call continues from the previous result. Scalars only:
anything that is not an `int` or a `float` raises `TypeError("Error")`, and
booleans are rejected explicitly because `bool` subclasses `int`. The subject
repeats that globals are forbidden.

The chain compounds: `3 -> 9 -> 81 -> 6561`, not `3 -> 9 -> 9 -> 9`.

## The concept

`outer` is a closure factory. Each call creates a frame holding `x`, `count` and
`function`, defines `inner` in that frame, and returns it. The frame is gone once
`outer` returns, but the names `inner` uses are stored in cells, so
`inner.__closure__` keeps them alive. `inner.__code__.co_freevars` names those
cells, and two calls to `outer` create two independent sets, which is why the
square chain and the power chain never interfere.

The load-bearing line is `count = function(count)`. `inner` reads the enclosing
`count` and rebinds it, so the value returned by one call becomes the argument of
the next. That is the difference between `function(x)` and
`count = function(count)`: the first returns a function of the original argument
forever, the second remembers.

Assignment decides scope at compile time. Without `nonlocal count`, the assignment
makes `count` local to `inner` for the whole body, so the read on the right-hand
side happens before the local exists and raises `UnboundLocalError`. The "no
global" rule removes the other tempting fix: `global count` would let the chain
work while moving the state into the module namespace, where every function shares
it and it outlives the closure. `nonlocal` keeps the state in the cell that
belongs to this `inner`.

`square` and `pow` are ordinary functions, so they are values like any other.
`outer` does not know which one it receives; it calls whatever is in its
`function` cell. Passing `square` to one call and `pow` to another is what lets a
single wrapper serve two behaviours.

The type guard is the other boundary. `isinstance(True, int)` is true, so the check
must reject booleans explicitly, and `square("a")` must raise `TypeError("Error")`
rather than return a value or a different exception.

## How to check

Run the tester from its directory. These lines are the real output.

```bash
cd Module_4/ex01
../.venv/bin/python tester.py
# 9
# 81
# 6561
# ---
# 1.8371173070873836
# 3.056683336818703
# 30.42684786675409
```

The closure can be inspected while it accumulates. `co_freevars` is alphabetical,
so the cells are `count` then `function`:

```bash
../.venv/bin/python -c \
  "from in_out import outer, square
c = outer(3, square)
c(); c()
print([cell.cell_contents for cell in c.__closure__])"
# [81, <function square at 0x...>]
```

The guard is tested directly. Both calls end in a traceback whose last line is:

```bash
../.venv/bin/python -c "from in_out import square; square('a')"
# TypeError: Error
../.venv/bin/python -c "from in_out import square; square(True)"
# TypeError: Error
```

The subject requires a docstring on every function, including the nested `inner`:

```bash
../.venv/bin/python -c "from in_out import outer; print(outer.__doc__)"
```

Lint from the module root:

```bash
cd Module_4
.venv/bin/flake8 ex00 ex01 ex02 ex03
```

Expect nothing: a clean tree prints nothing. flake8 cannot check the documentation
rule, which is why the `__doc__` audit stays manual.

## Key take away

State that outlives one call belongs in an enclosing scope, and mutating it needs
an explicit `nonlocal`. A closure is a counter with no module-level name to collide
with, and each factory call gets a fresh cell. Rebinding a captured name is what
makes the chain compound, so returning the new value is part of the contract. Type
guards belong at the boundary, and `bool` needs naming because it is an `int`. Two
closures built by the same factory prove the state is not shared.
