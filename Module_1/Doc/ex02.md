## 3. How an image becomes a NumPy array

```
JPEG file  ──Pillow──▶  PIL Image  ──convert("RGB")──▶  PIL Image (RGB)
                                                                     │
                                                                  np.array
                                                                     ▼
                                                     NumPy array of shape (H, W, 3)
```

### 3.1 The three dimensions of a colour image

```
arr[y][x][channel]
```

* **`y`** — the row, counted from the **top** (0 is the top row).
* **`x`** — the column, counted from the **left** (0 is the left column).
* **`channel`** — `0` is Red, `1` is Green, `2` is Blue.

The shape is therefore `(height, width, 3)`. For `landscape.jpg` that is
`(257, 450, 3)`: 257 pixels tall, 450 pixels wide, 3 colour channels.

A single pixel is `arr[y][x]`, an array of three numbers, for example `[19 42 83]`.

> **Watch the order.** NumPy uses **row-first** ordering `(y, x)`, whereas
> Matplotlib's `imshow` and most image APIs use `(x, y)`. This is the most common
> source of confusion in ex03 and ex04.

### 3.2 Why `.convert("RGB")`?

JPEG files come in several colour models:

* **RGB** — 3 channels (ordinary photographs),
* **L** — greyscale, 1 channel,
* **RGBA** — RGB plus an alpha (transparency) channel, 4 channels,
* **CMYK** — print colour model, 4 channels,
* **P** — palette-based.

Calling `.convert("RGB")` forces every image into the same 3-channel format, so the
shape `(H, W, 3)` always holds. Without it, a greyscale JPEG would produce `(H, W)`
and every shape check downstream would break.

## 4. Concepts

### 4.1 `pathlib.Path` — the modern way to handle paths

```python
from pathlib import Path

image_path = Path(path)
```

`Path` is an object that knows how to work with file-system paths. Compared with
string concatenation (`"../subject/" + name`), it is safer and platform-independent.

| Member | Behaviour |
|---|---|
| `Path("a/b.jpg")` | build a path object |
| `.is_file()` | `True` if the path exists **and** is a regular file |
| `.is_dir()` | `True` if it is a directory |
| `.exists()` | `True` if anything exists at that path |
| `.suffix` | the extension including the dot → `".jpg"` |
| `.stem` | the name without the extension → `"landscape"` |
| `.name` | the file name with extension → `"landscape.jpg"` |
| `.parent` | the containing directory |
| `.resolve()` | the absolute path |

### 4.2 `.suffix.lower()` — a case-insensitive extension check

```python
if image_path.suffix.lower() not in [".jpg", ".jpeg"]:
    raise ValueError("Unsupported format. Only (.jpg, .jpeg) are supported.")
```

* `.suffix` yields `".JPG"` for a file named `photo.JPG`.
* `.lower()` normalises it to `".jpg"`, so the check succeeds whatever the case.
* This satisfies *"You have to handle, at least, JPG and JPEG format"*: both
  extensions are accepted, and everything else is rejected with a clear message.

### 4.3 The `with` statement (context manager)

```python
with Image.open(image_path) as img:
    img_rgb = img.convert("RGB")
    img_array = np.array(img_rgb)
```

* `Image.open(...)` returns a `PIL.Image` object. It is **lazy**: the file is only
  really read when the pixels are requested.
* `with ... as img:` guarantees that the file handle is **closed automatically** when
  the block ends, even if an exception is raised inside it.
* Inside the block `img` is the open image; outside it the name still refers to the
  object, but the file is closed.
* **Why it matters:** without `with`, every call would leak a file descriptor, and
  the process would eventually fail with *"too many open files"*.

### 4.4 `np.array(pil_image)` — the bridge

```python
img_array = np.array(img_rgb)
```

`np.array()` on a PIL image reads the raw pixel buffer and wraps it in a NumPy array
of shape `(H, W, 3)` with dtype `uint8`.

* `uint8` means **unsigned 8-bit integer**, range `0`–`255` — exactly the range of
  one colour channel. This is why `255 - pixel` inverts a colour perfectly.
* The conversion copies the pixel data (257 × 450 × 3 = 346 950 bytes for
  `landscape.jpg`), not the file itself.

### 4.5 `UnidentifiedImageError`

```python
from PIL import Image, UnidentifiedImageError
```

Pointing Pillow at a file that is not a valid image — a PDF, a text file, a
corrupted JPEG — raises `UnidentifiedImageError`. Importing it explicitly makes it
possible to catch it and print a readable message instead of a traceback.

### 4.6 The `except` tuple

```python
except (FileNotFoundError, ValueError, TypeError, UnidentifiedImageError) as error:
    print(f"Error in ft_load: {error}")
    return None
```

Four exception types are caught because there are four ways the call can fail:

| Exception | Raised when |
|---|---|
| `FileNotFoundError` | the path does not exist |
| `TypeError` | the argument is not a `str` |
| `ValueError` | the extension is neither `.jpg` nor `.jpeg` |
| `UnidentifiedImageError` | the file exists but is not a valid image |

The subject states: *"Any exception not caught will invalidate the exercises."*

### 4.7 `-> np.ndarray | None` — the optional return type

```python
def ft_load(path: str) -> np.ndarray | None:
```

The `|` means "**either** a NumPy array **or** `None`". Returning `None` is the
standard way to signal failure, and the caller must check it:

```python
img_array = ft_load("../subject/landscape.jpg")
if img_array is None:
    return
```

> **A trap worth remembering.** `if not img_array:` would be **wrong**: a NumPy
> array with more than one element raises *"ValueError: The truth value of an array
> with more than one element is ambiguous"*. The comparison must be explicit:
> `if img_array is None:`.

## 5. Implementation walkthrough

`ex02/load_image.py`:

```python
try:
    if not isinstance(path, str):
        raise TypeError("Path must be a string.")

    image_path = Path(path)

    if not image_path.is_file():
        raise FileNotFoundError(f"File not found: {path}")

    if image_path.suffix.lower() not in [".jpg", ".jpeg"]:
        raise ValueError(
            "Unsupported format. Only (.jpg, .jpeg) are supported.")

    with Image.open(image_path) as img:
        img_rgb = img.convert("RGB")
        img_array = np.array(img_rgb)

        print(f"The shape of image is: {img_array.shape}")
        return img_array

except (FileNotFoundError, ValueError, TypeError, UnidentifiedImageError) as error:
    print(f"Error in ft_load: {error}")
    return None
```

The pipeline is: **check the type → check the file exists → check the extension →
open it → convert to RGB → build the array → print the shape → return it.**

Two details:

1. The `print` and the `return` sit **inside** the `with` block, but they only
   depend on `img_array`, which already holds the pixel data. Returning from inside
   a `with` block is safe — the file is still closed automatically.
2. The subject asks the function to *"print its format"*. In this exercise "format"
   means the **shape** of the array (`(257, 450, 3)`), which is what the expected
   output shows and what the implementation prints with the same wording:
   `The shape of image is: (257, 450, 3)`.

## 8. Key takeaways

1. **A colour image is a 3D NumPy array** of shape `(height, width, 3)`, indexed
   `arr[y][x][channel]` with channels R, G and B.
2. **`.convert("RGB")` normalises every image** to 3 channels — always apply it, or
   the shape will vary from file to file.
3. **`np.array(pil_image)`** is the one-liner that turns a picture into data.
4. **Always use `with` when opening a file** — the handle is closed automatically.
5. **`Path`** is safer than string concatenation, and `.suffix.lower()` handles
   `.JPG`, `.jpeg` and `.JPEG` alike.
6. **Return `None` on error and test it with `is None`** — `if not arr:` raises
   *"truth value of an array is ambiguous"*.
7. **Catch the exception types that can actually be named.** A long `except` tuple
   with a clear message is exactly what the subject asks for.
